Use P1's locked dependencies and local PostgreSQL/TLS installation instructions. No additional dependency or provider account is required. P1 authentication mode is still named `production` but this **does not deploy or certify production readiness**. It requires explicit acknowledgement, HTTPS and a loopback PostgreSQL URL. With a securely configured local `DATABASE_URL`, apply migrations explicitly from `backend`:

```bash
../.venv/bin/python -m app.migrate up
../.venv/bin/python -m app.corporate up
```

Provision your sole administrator with P1's interactive password CLI, then designate that existing account as Corporate owner from a local interactive terminal:


Passwords must be entered only at the protected interactive prompt. No seeded production password, credentials in command arguments, secret values in documentation, or registration endpoint. Owner designation is immutable; there is no reassignment API. Verify the actual human owner before designating the account. Never designate a bot's account. Start the existing P1 HTTPS server with `--no-access-log --no-proxy-headers`; build using `npm --prefix frontend run build`, then open `/corporate` and sign in.

Corporate migration version **1** lives in `corporate_schema_migrations` and `corporate.*.sql`; P1 schema version **1** and its migrations are untouched. `app.corporate down --confirm-disposable-database astro_test_g2` works only when configured to that exact disposable `astro_test_*` database. ## API and failure contracts

All routes use the existing credential-backed cookie session. Writes require the exact Origin and CSRF token plus active administrator status; every Corporate read/write then checks the single designated owner in the database. Unknown body fields are forbidden, so clients cannot supply repository URLs, principal kinds, approval owners or credentials. The existing 4096-byte request cap still applies.

| Method/path | Body / result |
|---|---|
| GET `/api/corporate/snapshot` | Projects, work, approvals, jobs, audit, costs, blocked connection metadata; newest 100 rows per list |
| POST `/api/corporate/projects` | `{name}`; repository is selected by the server, not caller |
| POST `/api/corporate/work` | `{project_id, request_key, title, objective, acceptance}`; immutable record and SHA256 digest |
| POST `/api/corporate/work/{id}/approve` | `{digest, confirmation: "APPROVE_ZERO_COST_CONTRACT"}`; distinct owner approval, maximum 0 cents |
| POST `/api/corporate/work/{id}/dispatch-contract` | `{reserve_cents: 0}` (default 0); matching unexpired approval required, atomic job+reservation+audit; **blocked live dispatch** |
| POST `/api/corporate/jobs/{id}/actual` | `{cents: 0, reference}`; exactly one idempotent zero-cost actual per job |

`request_key` and actual-cost reference use 1–64 ASCII letters/digits/underscore/hyphen. Same intake key and content returns the same record; a different digest with that key returns 409. Same approved work returns one job/marker under concurrent retries. Same actual reference/job returns one actual; conflicting references return 409. Project creation is not an external issue action and does not have a retry key. An approval cannot change submitted fields; edits require a new intake. Once an approval expires, create a new intake with a new request key and deliberately approve it; old work remains immutable. The UI shows expiry and hides expired contract actions. Bounded lists are documented MVP views, not deletion or complete pagination.

Failures: 401 missing/expired/revoked session; 403 invalid Origin/CSRF or viewer mutation; 404 Corporate in demo; 409 non-owner, blocked owner, missing/current approval, invalid digest/confirmation, conflicting request, nonzero spend or unknown Corporate version; 422 invalid/extra body; 413 oversized body; 503 database/schema unavailable. Errors omit submitted bodies, driver messages and credentials. All responses inherit P1 security headers. A blocked contract preparation returns a **200 local record** with explicit blocked status; it is not a successful live dispatch.

Budget row locking serializes reservation/actual transactions. PostgreSQL CHECK constraints enforce 0 cents even if an application guard is bypassed. Audit inserts share each mutation's transaction. Approval/work/project/job/reservation/actual/audit records reject UPDATE, DELETE and TRUNCATE. This is append-only **within the application/database permission boundary**: a database owner/superuser can disable triggers or drop tables, so this is not externally tamper-proof storage. Production requires separate least-privilege roles and administrator controls before activation.

No credentials are accepted in structured fields or logged. Common credential-shaped text is rejected as defense in depth; regex cannot prove arbitrary free text contains no secret. **Never enter credentials or customer/personal data into intake, project names or references.** Corporate audit stores identifiers, fixed event names, timestamps and optional zero cents, not free-form submitted text. React escapes displayed text.
